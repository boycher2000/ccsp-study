## 3.1 理解雲端基礎設施元件
<!-- covers: 1,2,3,4,5,6 -->

> 一句話:雲端由實體、網路、運算、虛擬化、儲存六層堆起來,最上面再蓋一層管理平面控制全部。

### 白話重點

| 元件 | 內容 | 安全重點 |
|---|---|---|
| 實體環境 | 機房、電力、冷卻、門禁 | CSP 負責;靠稽核報告與認證取得保證 |
| 網路與通訊 | 虛擬網路、負載平衡、DNS、CDN、跨區連線 | 分段、加密、流量檢查 |
| 運算 | 裸機、虛擬機、容器、無伺服器 | 映像強化、修補、隔離 |
| 虛擬化 | Hypervisor、容器執行環境 | 逃逸、側通道、VM sprawl |
| 儲存 | 區塊、物件、檔案、複寫 | 加密、存取、殘留 |
| 管理平面 | 建立、設定、刪除資源的 API 與控制台 | **最高權限、最大攻擊面** |

#### 管理平面(management plane)

- 所有資源都靠它創建與管理。一旦被攻破,攻擊者可以:刪除資源、複製資料、開出惡意資源、關閉日誌。
- 防護:**強制 MFA、最小權限、特權存取管理、限時授權、不使用 root、記錄所有 API 呼叫、獨立的稽核帳號**。
- 客戶也有自己的管理平面(例如 Kubernetes 控制平面),同樣要保護。

#### Hypervisor 類型

- **Type 1(裸機)**:直接跑在硬體上,效能與隔離較好,是雲端主流。
- **Type 2(寄居)**:跑在作業系統上,多用於桌面與測試。
- 現代技術(如 KVM)界線模糊,教科書二分法僅為簡化。

### 名詞解釋

- **Hypervisor escape**:客體突破隔離,攻擊主機或其他客體。
- **Side-channel attack**:利用共享硬體(快取、時序)洩漏資訊。
- **VM sprawl**:虛擬機無管控地增加。
- **SDN**:軟體定義網路,控制平面與資料平面分離。

### 延伸知識:軟體定義與隔離層次

- **SDN(軟體定義網路)**:把網路的**控制平面**(決定流量怎麼走)與**資料平面**(實際轉送)分離,集中以軟體管理。好處:靈活、可編排、可自動化;風險:控制器成為高價值目標。
- **隔離強度**(一般而言,取決於實作):VM(hypervisor 隔離)> 容器(共享核心,靠命名空間與 cgroup)> 行程。需要更強隔離的容器可用 microVM 或沙箱執行環境。
- **共享的資源**:CPU 快取、記憶體頻寬、網路、儲存後端,是側通道攻擊的來源。
- **邊界**:租戶邊界在虛擬網路、帳號與身分,不是實體邊界。

| 責任 | IaaS | PaaS | SaaS |
|---|---|---|---|
| 實體、虛擬化 | CSP | CSP | CSP |
| 虛擬網路設定 | 客戶 | 部分 | CSP |
| 管理平面帳號與權限 | 客戶 | 客戶 | 客戶(租戶管理) |

### 情境演練

雲端帳號的 root 金鑰被寫在公開程式碼庫,攻擊者開出大量運算資源挖礦。**原因**:管理平面存取不當。**預防**:不使用 root、MFA、短期憑證、用量與費用告警、程式碼庫機密掃描。

### 考點與陷阱

> Tip:題目問「被攻破後影響最多租戶或資源」,答管理平面。

> 陷阱:把客體作業系統的漏洞當成 hypervisor 漏洞。前者影響單一實例,後者影響多租戶。

## 3.2 設計安全的資料中心
<!-- covers: 1,2,3,4 -->

> 一句話:資料中心的安全來自邏輯分割、選址、環境控制與各種備援,缺一不可。

### 白話重點

#### 邏輯設計

- **租戶分割(tenant partitioning)**:帳號、網路、身分、金鑰、儲存各層都分開。
- **存取控制**:分層、最小權限、分離管理與資料平面。

#### 實體設計

- **選址**:避開地震、洪水、颱風、斷層;評估鄰近風險(機場、化工廠)、電力與網路供應、**法規與地緣政治**。
- **自建或租用(buy or build)**:自建控制高、成本高、時程長;託管或租用(colocation)快、但需信任第三方。

#### 環境設計

- **HVAC(暖通空調)**:溫度與濕度控制;冷熱通道;空調備援。
- **多供應商路徑連線(multi-vendor pathway connectivity)**:使用不同電信商、不同進線路徑,避免單一施工或業者故障斷線。

#### 韌性設計

- **電力**:雙路市電、UPS、發電機、N+1 或 2N 備援、燃料儲備。
- **空調**:備援機組。
- **連線**:多條且實體路徑分離的光纖。
- 分級參考:**Uptime Institute Tier I–IV**(Tier III:可同時維護;Tier IV:容錯)、**ANSI/TIA-942**。

### 名詞解釋

- **N+1 / 2N**:多一份備援 / 完整的雙套。
- **Colocation**:租用機櫃與空間。
- **Hot/cold aisle**:冷熱通道。
- **Concurrent maintainability**:維護時不需停機。

### 延伸知識:資料中心分級與環境控制

#### Uptime Institute Tier

| Tier | 特性 | 預期可用度(參考) |
|---|---|---|
| I | 基本容量,單一路徑,無備援 | 約 99.671% |
| II | 備援容量元件,單一路徑 | 約 99.741% |
| III | **可同時維護**(維修不停機),多路徑 | 約 99.982% |
| IV | **容錯**,可承受單一故障 | 約 99.995% |

> 待核對:各 Tier 的可用度百分比為常見引用值,請對照 Uptime Institute 官方說明。

#### 環境控制

- **溫濕度**:依業界建議範圍控制;過乾增加靜電,過濕造成凝結與腐蝕。
- **冷熱通道配置**:避免熱空氣回流。
- **防火**:偵測(煙霧、極早期偵測)加滅火。電子設備常用**乾式或潔淨氣體**滅火,避免水損;濕式管路水損風險較高,需權衡。
- **電力**:雙路市電、UPS(銜接)、發電機(長時間)、定期負載測試。
- **水損**:漏水偵測、機房高架地板。

#### 實體存取

- 多層邊界:圍籬、保全、門禁、**人員陷阱(mantrap)**、生物辨識、機櫃鎖、監視與紀錄。

### 情境演練

客戶要求 99.99% 的設施可用度。**判斷**:需要容錯等級的設計(例如 Tier IV 或相當),並檢視連線與電力是否皆有路徑分離;只靠單一電信商與單路電力不符。

### 考點與陷阱

> Tip:兩家電信商、從不同方向進線,支援的是連線韌性(multi-vendor pathway connectivity)。

> 陷阱:兩家電信商共用同一條管溝,仍是單點故障。路徑要實體分離。

## 3.3 分析雲端基礎設施與平台風險
<!-- covers: 1,2,3 -->

> 一句話:辨識資產與威脅、評估衝擊與機率,再決定避免、降低、轉移、分擔或接受。

### 白話重點

#### 風險評估

- **辨識**:資產、威脅、弱點、現有控制。
- **分析**:
  - **定性**:高/中/低。
  - **定量**:SLE(單次損失期望)、ARO(年發生率)、**ALE = SLE × ARO**。
- 雲端特別:要涵蓋**供應商**、共享技術、依賴關係、法規與落地。

#### 雲端弱點、威脅與攻擊

- 設定錯誤與暴露的管理介面。
- 身分被盜、憑證外洩。
- 管理平面濫用。
- 多租戶隔離失敗、hypervisor 逃逸、側通道。
- 不安全的 API。
- 供應鏈(映像、套件)。
- 拒絕服務與經濟型拒絕服務(EDoS,讓你的帳單暴增)。
- 內部威脅,包含 CSP 人員。

#### 風險處置策略

| 策略 | 說明 | 例子 |
|---|---|---|
| Avoid(避免) | 停止會產生風險的活動 | 不在高風險國家存放資料 |
| Mitigate(降低) | 降低機率或衝擊 | 加密、MFA、備援 |
| Transfer(轉移) | 把財務損失轉給第三方 | 網路保險、合約賠償 |
| Share(分擔) | 與他人共同承擔 | 責任分擔合約、共保 |
| Accept(接受) | 不採取額外措施 | 風險低於風險胃納 |

> 備註:有些框架把 share 併入 transfer。大綱兩者都列。

> 重點:轉移的是**財務損失**,不轉移責任、法律義務或聲譽損害。

### 名詞解釋

- **Risk appetite / tolerance**:風險胃納 / 可容忍度。
- **Residual risk**:處置後剩餘的風險。
- **Inherent risk**:未加控制前的風險。
- **EDoS**:經濟型拒絕服務。

### 延伸知識:風險登記表與雲端常見威脅

#### 風險登記表(risk register)

| 欄位 | 內容 |
|---|---|
| 風險描述 | 事件與原因、後果 |
| 資產 | 受影響的資料或服務 |
| 機率、衝擊 | 定性或定量 |
| 風險等級 | 機率 × 衝擊 |
| 處置策略 | 避免、降低、轉移、分擔、接受 |
| 負責人與期限 | 誰、何時完成 |
| 殘餘風險 | 處置後剩餘 |

#### 定量範例

- 資產價值 100 萬、一次事件損失 40%:**SLE = 40 萬**。
- 預期每 4 年發生一次:**ARO = 0.25**。
- **ALE = 40 萬 × 0.25 = 10 萬 / 年**。
- 控制措施年成本 3 萬,可把 ARO 降到 0.05(ALE = 2 萬):效益 = 10 − 2 − 3 = **5 萬**,值得做。

#### 雲端常見威脅(CSA 的威脅清單,概念層面)

- 設定錯誤與變更控制不足、身分與存取管理不善、不安全的介面與 API、帳號劫持、內部威脅、資料外洩、供應鏈與第三方風險、缺乏雲端安全架構與策略。

> 待核對:CSA 的威脅清單每次版本名稱與排序不同,請以最新版本為準。

### 情境演練

管理層問:「雲端有保險與供應商的賠償條款,是不是就可以不做加密?」**回答**:保險轉移的是財務損失;外洩的聲譽、法規責任與客戶信任無法轉移,仍要降低機率與衝擊。

### 考點與陷阱

> Tip:購買保險屬於 transfer,不是 mitigate。

> 陷阱:處置完還有殘餘風險,需要明確接受並記錄。

## 3.4 規劃與實作安全控制
<!-- covers: 1,2,3,4 -->

> 一句話:控制要涵蓋實體、系統、通訊、身分與稽核,並釐清哪些由 CSP、哪些由客戶負責。

### 白話重點

#### 實體與環境保護

- 門禁、監控、防火、防水、電力、空調。
- 雲端中由 CSP 負責;混合雲或本機房的部分客戶要自己做。
- 客戶以**稽核報告與認證**取得保證。

#### 系統、儲存與通訊保護

- **系統**:強化、修補、基準、端點防護。
- **儲存**:加密、存取控制、備份。
- **通訊**:TLS、VPN、分段、微分段、私有連線。

#### 身分識別、驗證、授權

- 識別(你是誰)→ 驗證(證明)→ 授權(能做什麼)→ 記錄(做了什麼)。
- **MFA**、**聯邦身分**、**最小權限**、**職務分離**。
- 雲端特有:工作負載身分、短期憑證。

#### 稽核機制

- **日誌收集**:管理平面稽核日誌、資料事件日誌、網路流量日誌。
- **關聯分析(correlation)**:把不同來源的事件串起來(SIEM)。
- **封包擷取(packet capture)**:保留通訊內容,事後可重建;雲端需要供應商提供鏡像或擷取能力。

### 名詞解釋

- **Microsegmentation**:細緻到工作負載層級的網路分段。
- **Workload identity**:機器與服務的身分。
- **Log correlation**:跨來源事件關聯。
- **Traffic mirroring**:鏡像流量供分析。

### 延伸知識:控制的分類方式

#### 依功能

| 類型 | 作用 | 例子 |
|---|---|---|
| 預防(preventive) | 阻止事件發生 | 防火牆、MFA、加密 |
| 偵測(detective) | 發現事件 | IDS、日誌、監控 |
| 矯正(corrective) | 事後修復 | 修補、還原備份 |
| 威嚇(deterrent) | 讓人不敢做 | 警告標語、監視器 |
| 補償(compensating) | 無法做標準控制時的替代 | 無法修補時加隔離與監控 |
| 復原(recovery) | 恢復正常 | DR 站點 |

#### 依性質

- **管理性**(政策、訓練)、**技術性**(防火牆、加密)、**實體**(門禁、鎖)。

#### 縱深防禦

- 多層控制,單層失效不致全盤失守:實體 → 網路 → 主機 → 應用 → 資料 → 身分。
- **最小權限、職務分離、失效安全(fail safe)**。

#### 雲端的控制責任

| 控制 | IaaS | PaaS | SaaS |
|---|---|---|---|
| 實體安全 | CSP | CSP | CSP |
| 網路控制 | 客戶設定 | 部分 | CSP |
| 身分與存取 | 客戶 | 客戶 | 客戶 |
| 資料加密設定 | 客戶 | 客戶 | 客戶(依功能) |

### 情境演練

某舊系統無法修補已知漏洞,又不能立刻下線。**補償控制**:網路隔離、限制來源、加強監控與 WAF 規則,並設定下線期限與風險接受紀錄。

### 考點與陷阱

> Tip:事後要重建通訊內容,封包擷取才能取得內容;日誌通常只有事件與中繼資料。

> 陷阱:以為雲端不需要實體控制。客戶仍要靠稽核報告確認 CSP 的實體安全。

## 3.5 規劃營運持續與災難復原
<!-- covers: 1,2,3 -->

> 一句話:先定義業務能承受什麼(RTO、RPO、MTD),再選對應的備援層級,並實際演練。

### 白話重點

#### 關鍵指標

| 指標 | 意義 | 小技巧 |
|---|---|---|
| MTD / MTPD | 業務能承受的最長中斷時間 | 業務上限 |
| RTO | 服務必須在多久內恢復 | 必須 ≤ MTD |
| RPO | 可容忍丟失多少時間的資料 | 決定備份或複寫頻率 |
| WRT | 恢復後驗證與回復營運需要的時間 | MTD ≥ RTO + WRT |
| Recovery service level | 災難期間要恢復到什麼服務水準 | 不一定要 100% |

> 口訣:**RTO 看「時間」,RPO 看「資料」。**

#### DR 模式(成本與復原速度隨之遞增)

| 模式 | 說明 |
|---|---|
| Backup and restore | 只備份,災難時重建 |
| Pilot light | 核心資料與最小環境持續運行,災難時擴大 |
| Warm standby | 縮小規模的完整環境持續運行 |
| Multi-site active-active | 多地同時服務,近乎零中斷 |

#### 計畫生命週期

1. **建立**:依 BIA 與風險評估。
2. **實作**:流程、人員、工具、自動化。
3. **測試**:清單檢查 → 桌面推演(tabletop)→ 模擬 → 並行 → 完整中斷。
4. **維護**:依測試結果與環境變更更新。

> 重點:**未測試的計畫等於假設**。

### 名詞解釋

- **BCP vs DRP**:營運持續計畫(維持業務)/ 災難復原計畫(恢復 IT)。
- **Failover / Failback**:切換到備援 / 切回主站。
- **Availability zone / Region**:可用區 / 區域。
- **Shared fate**:共享相依的失效。

### 延伸知識:備份型態與演練

#### 備份型態

| 型態 | 備份什麼 | 備份速度 | 還原 |
|---|---|---|---|
| 完整(full) | 全部資料 | 最慢 | 最簡單,一份即可 |
| 增量(incremental) | 自上次**任一**備份後的變更 | 最快 | 需要完整備份加上所有增量,最慢 |
| 差異(differential) | 自上次**完整**備份後的變更 | 中 | 需要完整備份加最後一份差異 |

> 口訣:**增量只備上次以來,差異累計到上次完整。**

#### 3-2-1 原則

- **3** 份副本、**2** 種不同媒體、**1** 份異地(離線或不可變更佳,防勒索)。

#### BIA 步驟

1. 辨識業務流程與相依(人、系統、供應商)。
2. 評估中斷衝擊(財務、法規、聲譽)隨時間變化。
3. 決定 MTD、RTO、RPO 與優先順序。
4. 對應所需資源與備援策略。

#### 雲端 DR 注意

- 區域層級失效要靠**跨區域**;可用區只防機房或機櫃層級。
- 設定、機密、IaC 與金鑰也要備份,不只是資料。
- **演練**:包含切換與回切(failback)、人員聯絡與決策流程。

### 情境演練

某系統 RPO 為 15 分鐘,現行每日一次夜間完整備份。**結論**:不符合;需要持續複寫或頻繁增量與交易日誌備份,才能達到 15 分鐘的資料損失上限。

### 考點與陷阱

> Tip:RTO 4 小時、RPO 15 分鐘:服務 4 小時內恢復,最多可損失 15 分鐘的資料。

> 陷阱:RTO 不是 MTD。RTO 是技術目標,MTD 是業務上限。

> 陷阱:多可用區不等於多區域;區域性災難要靠跨區域。
