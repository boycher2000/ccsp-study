## 1.1 理解雲端運算概念
<!-- covers: 1,2,3,4 -->

> 一句話:雲端是「透過網路、隨需取用、按用量計費的共享資源池」,六大特性就是它的定義。

### 白話重點

- **定義(NIST SP 800-145)**:雲端運算是一種模型,讓人能透過網路,方便地、隨需地存取一個可設定資源的共享池(網路、伺服器、儲存、應用、服務),並能快速配置與釋放,只需極少管理或與供應商互動。
- **雲端不等於虛擬化**:虛擬化是技術,雲端加上了自助、彈性、計量與池化。
- **雲端不等於外包機房**:重點是服務模型與責任分擔,不是機器放哪裡。

#### 六大特性(NIST 五項加 ISO/IEC 17788 的 multi-tenancy)

| 特性 | 白話 | 安全意涵 |
|---|---|---|
| On-demand self-service | 客戶自己用控制台或 API 開資源,不用等人 | 權限管理要嚴,否則任何人都能開出昂貴或高風險資源 |
| Broad network access | 透過標準網路機制,各種裝置都能連 | 暴露面變大,身分與傳輸保護是主防線 |
| Resource pooling | 供應商把資源集中成池,動態分配給多個客戶 | 資料殘留、隔離失敗風險 |
| Rapid elasticity and scalability | 依需求快速放大或縮小 | 自動化擴縮的映像與設定必須事先強化 |
| Measured service | 用多少、計多少 | 計量資料可用於稽核與異常偵測(例如挖礦造成的暴增) |
| Multi-tenancy | 多個租戶共用同一套資源,彼此邏輯隔離 | 租戶隔離是雲端安全的核心前提 |

> 口訣:**自、網、池、彈、量、租**(自助、網路、池化、彈性、計量、多租戶)。

#### 角色(依 ISO/IEC 17789)

| 角色 | 做什麼 |
|---|---|
| Cloud Service Customer(CSC) | 使用雲端服務的組織或個人 |
| Cloud Service Provider(CSP) | 提供雲端服務 |
| Cloud Service Partner | 協助 CSP 或 CSC 的第三方,例如開發者、稽核者、整合商、**broker** |
| Cloud Service Broker | 在客戶與供應商之間仲介 |
| Regulator | 大綱列入角色,但嚴格說是外部利害關係人,不是 ISO 17789 定義的雲端 actor |

#### 構成技術

- **虛擬化**:把硬體抽象成多個虛擬資源,靠 hypervisor 實現。
- **儲存**:區塊、物件、檔案。
- **網路**:虛擬網路與 SDN(軟體定義網路)。
- **資料庫**:託管關聯式與 NoSQL。
- **編排(orchestration)**:協調多個自動化工作,如 Kubernetes、基礎設施即程式碼(IaC)。

### 名詞解釋

- **Tenant(租戶)**:使用共享環境的客戶單位。
- **Multi-tenancy vs Resource pooling**:池化是供應商端「資源集中共用」的作法;多租戶是「多個客戶共用同一個環境並保持隔離」的結果。
- **Elasticity vs Scalability**:elasticity 強調自動、雙向、短時間內調整;scalability 是系統增加容量的能力。
- **Broker 的三種功能**:intermediation(加值仲介)、aggregation(整合多家服務)、arbitrage(在多家之間挑選最佳)。
- **Orchestration vs Automation**:自動化是做一件事;編排是協調一連串自動化任務。

### 考點與陷阱

> Tip:題目描述「整合多家雲服務、提供單一介面、代為議價」,答 broker,不是 partner。

> 陷阱:把 resource pooling 與 multi-tenancy 混為一談。前者是資源共用的方式,後者是客戶共存且需隔離。

> 陷阱:誤以為 regulator 提供雲端服務。它是監管角色,會影響合規要求。

## 1.2 描述雲端參考架構
<!-- covers: 1,2,3,4,5,6 -->

> 一句話:參考架構告訴你「誰做什麼、雲端服務分哪幾種、怎麼部署、要權衡哪些共同考量」。

### 白話重點

#### 雲端運算活動(依 ISO/IEC 17789)

- 這個子項在大綱以「活動」為單位:各角色的工作,例如客戶使用服務、管理服務、做商業管理;供應商提供服務、營運、支援、安全與風險管理。概念層級理解即可。
- 實務上拆成:**規劃與選型 → 導入與移轉 → 營運與監控 → 退場(reversibility)**。

#### 服務能力類型與服務類別

| 類別 | 客戶得到什麼 | 例子 |
|---|---|---|
| IaaS | 運算、儲存、網路等基礎資源 | 虛擬機、虛擬網路 |
| PaaS | 開發與執行平台 | 託管資料庫、應用平台、無伺服器 |
| SaaS | 完整應用程式 | 電子郵件、CRM |

- ISO/IEC 17788 另列 CaaS(通訊)、DSaaS(資料儲存)、NaaS(網路)等。
- 能力類型對應:應用能力(application)→ SaaS;平台能力(platform)→ PaaS;基礎設施能力(infrastructure)→ IaaS。

#### 部署模型

| 模型 | 說明 | 重點 |
|---|---|---|
| Public | 供應商向一般大眾提供,多租戶 | 成本低、控制較少 |
| Private | 單一組織專用 | 控制高、成本高 |
| Hybrid | 私有與公有整合,資料與應用可在之間流動 | 整合與一致性管理困難 |
| Community | 共享給有共同關注(例如合規)的組織 | 治理需要共識 |
| Multi-cloud | 使用多家 CSP | 降低鎖定風險,但管理複雜度上升 |

> 陷阱:hybrid(私有加公有的整合)與 multi-cloud(多家 CSP)不是同一件事。

#### 共同考量(Cloud shared considerations)

| 考量 | 白話 |
|---|---|
| Interoperability | 不同系統能一起運作 |
| Portability | 資料與應用搬到別的環境的難易度 |
| Reversibility | 終止服務時客戶取回資料與成品、供應商清除 |
| Availability | 需要時能使用 |
| Security / Privacy | 保護與個資處理 |
| Resiliency | 承受並從故障恢復 |
| Performance | 效能達標 |
| Governance | 政策與決策機制 |
| Maintenance and versioning | 維護與版本變更對客戶的影響 |
| SLA | 可量化服務承諾與補償 |
| Auditability | 能被稽核 |
| Regulatory | 法規遵循 |
| Outsourcing | 外包後責任仍在客戶 |

> 重點:外包只轉移作業,**不轉移責任**(accountability)。

#### 相關技術的影響

| 技術 | 對雲端安全的意涵 |
|---|---|
| 資料科學、ML、AI | 需要大量資料,資料來源與隱私變成風險;模型本身成為資產 |
| 區塊鏈 | 不可竄改帳本,但資料一旦寫入難以刪除,與刪除權衝突 |
| IoT | 大量低資源裝置,更新與身分管理困難 |
| 容器 | 輕量、快速,共享核心,映像與供應鏈安全重要 |
| 量子運算 | 威脅現行公鑰加密,需規劃後量子密碼 |
| 邊緣運算 | 資料在靠近來源處理,實體與管理分散 |
| 機密運算(confidential computing) | 用硬體受信任執行環境(TEE)保護**使用中**的資料 |

### 名詞解釋

- **Reversibility**:可退場性,終止合約時取回資料與清除。
- **Interoperability vs Portability**:前者是共同運作;後者是搬移。
- **TEE(Trusted Execution Environment)**:隔離且受保護的執行區域。
- **Post-quantum cryptography**:能抵抗量子電腦攻擊的演算法。

### 考點與陷阱

> Tip:題目描述「合約結束時取回資料並確認刪除」,答 reversibility;「搬到另一家」,答 portability;「兩套系統能對話」,答 interoperability。

> 陷阱:SLA 只描述服務水準與補償,不等於安全保證。

## 1.3 理解與雲端相關的安全概念
<!-- covers: 1,2,3,4,5,6,7 -->

> 一句話:這是 D1 的安全工具箱:加密與金鑰、身分、清除、網路、虛擬化、威脅與基本衛生。

### 白話重點

#### 密碼學與金鑰管理

- **三種狀態**:靜態(at rest)、傳輸中(in transit)、使用中(in use,靠機密運算)。
- **金鑰管理**是整個加密的核心:誰產生、誰保管、怎麼輪替、怎麼撤銷、怎麼銷毀。
- **常見金鑰模型**:CSP 管理金鑰、客戶管理金鑰(CMK/BYOK)、客戶自己保管(HYOK)。控制權越高,責任越高。

#### 身分與存取

| 類型 | 說明 | 風險 |
|---|---|---|
| 使用者存取 | 員工與客戶登入 | 釣魚、密碼重用 |
| 特權存取 | 管理員與 root | 影響面最大,需要 PAM、JIT、MFA |
| 服務存取 | 工作負載、API、機器對機器 | 長期金鑰寫進程式碼 |

#### 資料與媒體清除(sanitization)

- **覆寫(overwriting)**:以隨機資料覆蓋。
- **加密抹除(cryptographic erase)**:銷毀金鑰使密文無法還原。雲端無法實體銷毀媒體時是首選。前提:資料一直用客戶控制的金鑰加密,且金鑰沒有其他副本。
- 消磁、粉碎屬實體手段,客戶在雲端通常做不到。

#### 網路安全

- **NSG / 安全群組**:依來源、目的、埠控制流量。注意各平台差異:AWS security group 為 stateful 且只有 allow;NACL 為 stateless 且可 deny;Azure NSG 有 allow 與 deny。
- **流量檢查**:IDS/IPS、WAF、防火牆。
- **地理圍欄(geofencing)**:依地理位置限制存取或資料落地。

#### 虛擬化安全

- **Hypervisor**:Type 1(裸機)、Type 2(寄居於作業系統)。威脅:逃逸、VM sprawl、側通道。
- **容器**:共享核心,映像安全、runtime 隔離、機密管理。
- **暫態運算(ephemeral)**:資源短命,重建取代修補。
- **無伺服器(serverless)**:客戶只管程式碼與設定;權限過大與事件注入是風險。
- **隔離**是目標:租戶與租戶之間、客體與主機之間。

#### 常見雲端威脅

- 設定錯誤、身分被盜、不安全的 API、資料外洩、內部威脅(含 CSP 人員)、帳號劫持、拒絕服務、共享技術漏洞。

#### 安全衛生(hygiene)

- **修補**、**基準(baseline)**、**強化(hardening)**。
- **不可變架構(immutable architecture)**:不就地修補,改用新映像重建並替換舊的。

### 名詞解釋

- **Crypto-shredding**:加密抹除的另一種說法。
- **PAM / JIT**:特權存取管理 / 限時授予權限。
- **VM sprawl**:虛擬機失控增長,無人管理。
- **Baseline**:組織核可的安全設定基準。
- **Immutable infrastructure**:基礎設施部署後不修改。

### 口訣與記憶

> 口訣:**加、身、清、網、虛、威、衛**(加密、身分、清除、網路、虛擬化、威脅、衛生)——7 個要點,各自一格。

### 考點與陷阱

> Tip:「客戶無法接觸實體媒體」的情境,首選加密抹除,不是消磁。

> 陷阱:金鑰與資料放在同一處,加密就失去意義。

> 陷阱:把服務存取當成使用者存取處理,長期金鑰寫進程式碼是常見的考題素材。

## 1.4 理解安全雲端設計原則
<!-- covers: 1,2,3,4,5,6,7 -->

> 一句話:設計要從資料生命週期、營運持續、責任分擔、避免鎖定與 DevOps 流程一起考慮。

### 白話重點

#### 雲端資料生命週期(CSA)

| 階段 | 重點控制 |
|---|---|
| Create | 分類、標籤、加密 |
| Store | 存取控制、加密、備份 |
| Use | 權限、DLP、使用中保護 |
| Share | 授權、傳輸加密、IRM |
| Archive | 長期保存、不可變、金鑰保存 |
| Destroy | 加密抹除、可驗證銷毀 |

#### 雲端 BC/DR 規劃

- 使用多區域、多可用區,資料複寫,自動化復原。
- 雲端提供 DR 的彈性,但**責任仍在客戶**:設定、測試、演練。
- RTO、RPO、MTD 與業務衝擊分析(BIA)連動。

#### BIA 與成本效益(CBA、ROI)

- **BIA**:辨識關鍵業務流程,估算中斷的衝擊,決定復原優先順序。
- **CBA**:比較控制措施的成本與避免的損失。
- **ROI**:投資報酬率,用於說明資安投資。

#### 功能性安全需求

- **Portability**、**interoperability**、**vendor lock-in**:設計時就要預留退場與替代方案,例如標準格式、容器化、抽象層、多雲策略。

#### 各服務類別的安全考量與責任

- SaaS:客戶主要管資料、身分、設定與使用者行為;要審查供應商證據。
- PaaS:再加上應用安全與平台設定。
- IaaS:再加上作業系統、網路設定、修補與監控。

#### 設計模式

- **SANS 安全原則**:縱深防禦、最小權限、職務分離、失效安全(fail safe)等通用原則。
- **Well-Architected Framework**:各雲商發布的最佳實務框架(安全、可靠、效能、成本、營運卓越等支柱),不是中立標準。
- **CSA Enterprise Architecture**:CSA 提供的企業架構參考模型。
- **Secure by design**:從設計階段就把安全納入,而不是事後補強。

#### DevOps 安全

- **Shift-left**:早期測試。
- **IaC 掃描**:在部署前檢查基礎設施定義。
- **管線強化**:保護 CI/CD、簽署成品、機密管理、最小權限。
- **持續監控與回饋**。

### 名詞解釋

- **Vendor lock-in**:被供應商綁定,轉換成本高。
- **Fail safe vs Fail secure**:失效時保持安全(例如門鎖)與保持可用的取捨。
- **Defense in depth**:多層防禦。
- **IaC**:以程式碼描述並部署基礎設施。

### 考點與陷阱

> Tip:不論 IaaS、PaaS、SaaS,客戶對自己的資料與身分管理都保有責任。

> 陷阱:Well-Architected 是特定雲商的框架,不是「雲商中立」標準。

> 陷阱:雲端內建的 DR 功能不等於已完成 DR,仍要設定與測試。

## 1.5 評估雲端服務供應商
<!-- covers: 1,2 -->

> 一句話:選 CSP 時,用「準則加證據」檢驗,並確認證書的範圍真的涵蓋你要買的服務。

### 白話重點

#### 依準則驗證(verification against criteria)

- 先定義**準則**:法規、業務需求、安全要求、SLA、資料落地。
- 再蒐集**證據**:稽核報告、認證、問卷、合約、滲透測試摘要、實地或遠端評估。
- **驗證範圍**:證據必須涵蓋實際購買的服務、區域與組態。

#### 產品與子系統認證

| 標準 | 評估什麼 | 重點 |
|---|---|---|
| Common Criteria(ISO/IEC 15408) | 資訊技術**產品**的安全功能與保證 | 有 EAL1–EAL7;評估對象為 TOE;依 Protection Profile(PP)與 Security Target(ST) |
| FIPS 140 | **密碼模組**的安全要求 | 等級 1–4;大綱寫 FIPS 140-2;NIST 說 140-3 為現行受理標準 |

> 待核對:NIST CMVP 頁面表示 FIPS 140-2 模組在 2026-09-21 後移到 Historical 清單。考試以大綱字面為準,實務請看 140-3。

#### 常作為證據的其他資料(非大綱條目)

- ISO/IEC 27001(ISMS 認證)、27017(雲端控制)、27018(公有雲 PII 保護)。
- SOC 2 Type II、CSA STAR(含 CCM 與 CAIQ)。

### 名詞解釋

- **TOE(Target of Evaluation)**:被評估的產品與組態。
- **PP / ST**:Protection Profile(類別需求)/ Security Target(特定產品宣告)。
- **EAL**:Evaluation Assurance Level,越高代表驗證越嚴,不等於越安全或越適合。

### 延伸知識:怎麼實際評估一家 CSP

| 步驟 | 做法 |
|---|---|
| 1. 定義準則 | 法規、資料落地、RTO/RPO、加密與金鑰要求、稽核權、事件通報時限 |
| 2. 蒐集證據 | ISO/IEC 27001 認證與適用性聲明(SoA)、SOC 2 Type II、CSA STAR、滲透測試摘要、BCP/DR 測試結果 |
| 3. 核對範圍 | 證據涵蓋的服務、區域、期間、子服務組織是否包含你要用的 |
| 4. 評估殘餘風險 | 證據沒涵蓋的部分,用合約或客戶端控制補強 |
| 5. 持續監控 | 證書會過期、範圍會變,要定期重評 |

- **CSA STAR**:Level 1 為自評(以 CAIQ 回答);Level 2 為第三方稽核或認證;CCM(Cloud Controls Matrix)是控制對照框架。
- **ISO/IEC 27001 的適用性聲明(Statement of Applicability)**:列出哪些控制被採用,看它才知道範圍。

> 待核對:CSA STAR 各級的名稱與是否已有 Level 3,請對照 CSA 官方頁面。

### 情境演練

供應商給你一份 ISO/IEC 27001 證書,但範圍只寫「總公司資訊系統」,你要用的是其雲端服務。**正確判斷**:證書範圍不涵蓋你要用的服務,不能作為證據;要求提供涵蓋該服務的證據,或以合約與其他控制補強。

### 考點與陷阱

> Tip:拿到證書第一步:檢查評估範圍與組態是否對應你購買的服務。

> 陷阱:CC 或 FIPS 證書評估的是產品或模組,不等於整個雲端服務已通過驗證。

## 1.6 理解 AI/ML
<!-- covers: 1,2,3,4,5 -->

> 一句話:AI/ML 既是安全工具(偵測、編排),也是風險來源(資料、偏見、法規)。

### 白話重點

#### 雲端威脅偵測與分析

- **異常偵測**:建立正常行為基準,找出偏離。
- **UEBA**:使用者與實體行為分析。
- **分類與關聯**:把大量日誌分成已知攻擊模式。
- 限制:誤報、漏報、模型漂移、對抗式攻擊。

#### 資料來源驗證與確認

- 模型的品質取決於資料。要確認來源**可信、完整、時間同步、未被竄改、無系統性偏差**。
- 原則:garbage in, garbage out。
- 資料來源被污染(data poisoning)會讓模型學到錯誤。

#### SOAR

- **Security Orchestration, Automation and Response**。
- **編排**:串接多個工具;**自動化**:機器執行重複任務;**回應**:執行處置(封鎖、隔離、通知)。
- 與 SIEM 互補:SIEM 收集與關聯,SOAR 負責流程與處置。
- 高衝擊動作要保留人工審核(human-in-the-loop)。

#### 倫理

- 偏見與公平、透明度與可解釋性、隱私與比例原則、問責、雙重用途。

#### 法規

- GDPR 對自動化決策有規範(第 22 條)。
- 歐盟 AI Act 為專門針對 AI 的法規,採風險分級。
- 其他:行業監管、合約中的資料使用限制。

> 待核對:AI Act 的適用時程與風險分級細節,請對照 EUR-Lex 官方文本。

### 名詞解釋

- **Model drift**:模型隨資料分布改變而失準。
- **Data poisoning**:在訓練資料中植入錯誤資料。
- **Explainability**:能解釋模型為何做出某個判斷。
- **Human-in-the-loop**:關鍵決策要人工確認。

### 延伸知識:AI 在雲端的安全面向

| 面向 | 說明 |
|---|---|
| 監督式與非監督式 | 監督式需要標記資料(分類、預測);非監督式找結構與異常,常用於威脅偵測 |
| 模型漂移與重訓 | 資料分布改變會讓偵測失準,需持續監控與重訓 |
| 對抗式攻擊 | 刻意構造輸入躲過偵測(evasion),或污染訓練資料(poisoning) |
| 生成式 AI 風險 | Prompt injection、敏感資料外洩、幻覺(hallucination)、過度代理(excessive agency) |
| 影子 AI(shadow AI) | 員工私下使用未核可的 AI 工具,資料外流 |
| 託管 AI 服務的共同責任 | CSP 管模型與平台;客戶管資料、提示詞、存取控制與輸出使用 |

- **治理**:AI 使用政策、資料分類與可用範圍、人工複核、模型清單與風險評估。

### 情境演練

SOC 導入 ML 異常偵測後,告警量暴增,多為誤報,分析師開始忽略告警。**最佳做法**:回頭檢查資料來源品質與基準期間,調校閾值並加入回饋迴路;**不是**直接關掉模型或全自動封鎖。

### 考點與陷阱

> Tip:先驗證資料來源的完整性與品質,再談模型與自動化。

> 陷阱:高衝擊的自動回應(例如封鎖帳號)在驗證前直接上線,誤報會造成營運中斷。
