## 2.1 描述雲端資料概念
<!-- covers: 1,2,3 -->

> 一句話:先搞清楚資料現在在生命週期的哪一階段、被分散到哪裡、怎麼流動,才知道該用什麼控制。

### 白話重點

#### 雲端資料生命週期(CSA 六階段)

| 階段 | 發生什麼 | 重點控制 |
|---|---|---|
| Create | 產生或匯入資料 | 分類、標籤、建立時加密 |
| Store | 寫入儲存 | 靜態加密、存取控制、備份 |
| Use | 被應用處理或檢視 | 最小權限、DLP、機密運算 |
| Share | 提供給其他人或系統 | 授權、傳輸加密、IRM |
| Archive | 長期保存 | 不可變儲存、金鑰也要長期保存 |
| Destroy | 永久銷毀 | 加密抹除、可驗證 |

> 口訣:**建、存、用、享、封、毀**。

#### 資料分散(data dispersion)

- 把資料切成片段、複寫到多個位置(設備、可用區、區域)以提高**可用性與耐久性**。
- **糾刪碼(erasure coding)**:切成 k 個資料片加 m 個冗餘片,只要取得**達門檻數量**的片段就能重建,不是任意子集。
- 安全意涵:好處是單一位置失效不影響;風險是**你不知道每個片段實際在哪**,影響資料落地與刪除驗證。
- 分散與加密常搭配:片段本身是密文,單一片段外洩也無法讀取。

#### 資料流(data flows)

- 用**資料流圖(DFD)**畫出:資料從哪裡進來、經過哪些系統、存在哪、送到哪個第三方、是否跨境。
- 用途:找出需要加密與審查的節點、決定合規範圍、辨識外洩路徑。
- 雲端特有:API 呼叫、跨區域複寫、備份、日誌匯出、SaaS 整合都是資料流。

### 名詞解釋

- **Data residency**:資料實際存放的地理位置。
- **Data sovereignty**:資料受所在國法律管轄。
- **Durability vs Availability**:耐久性是資料不遺失;可用性是需要時能存取。
- **Replication**:複寫,提升可用性,也擴散了需要保護的副本數量。

### 延伸知識:生命週期的角色與位置

- **CSA 模型強調**:資料可以在任何階段出現在任何**位置**,並被不同**角色**以不同**裝置**存取。因此每個階段都要問:誰、在哪、用什麼存取、受什麼法規管。
- **階段不一定線性**:資料可能反覆 Use 與 Share,也可能直接封存。
- **資料位置與控制點**:資料離開自己控制的環境(Share)就要靠合約、加密與 IRM 延伸保護。

| 階段 | 常見失誤 |
|---|---|
| Create | 沒分類就存入,後面所有控制都失準 |
| Store | 備份與快照沒加密 |
| Use | 開發與測試環境使用正式資料 |
| Share | 分享連結永久有效、沒有存取記錄 |
| Archive | 加密金鑰沒有一起保存,日後無法解密 |
| Destroy | 只刪主資料,副本與快照仍在 |

### 情境演練

一家公司要把歸檔 10 年的加密資料取回,卻發現當年的金鑰管理服務已更換、金鑰遺失。**教訓**:封存要連同金鑰一併規劃長期保存與輪替,否則資料等同被銷毀。

### 考點與陷阱

> Tip:把資料經 API 提供給合作夥伴,屬於 Share 階段。

> 陷阱:糾刪碼不是「任一片段」就能重建,需達到門檻數量。

> 陷阱:資料分散提高可用性,但也讓「確認資料已全部刪除」更困難。

## 2.2 設計與實作雲端資料儲存架構
<!-- covers: 1,2 -->

> 一句話:不同儲存類型有不同存取方式與威脅,選型就決定了控制措施。

### 白話重點

#### 儲存類型

| 類型 | 特性 | 常見用途 |
|---|---|---|
| Long-term(封存) | 成本低、取回慢 | 合規保存、歸檔 |
| Ephemeral(暫態) | 實例停止或終止就消失 | 暫存、快取;不可放唯一副本 |
| Raw(原始) | 區塊層級,直接掛給 VM | 需要自行管理檔案系統 |
| Object(物件) | 扁平命名空間、中繼資料、REST API | 靜態內容、備份、資料湖 |
| Volume(磁碟區) | 區塊儲存掛載到實例 | 資料庫、作業系統磁碟 |

#### 各類型的主要威脅

| 類型 | 常見威脅 |
|---|---|
| Object | 權限設定錯誤、公開 bucket、過寬政策、金鑰外洩 |
| Volume | 快照外洩、未加密、被其他實例誤掛載 |
| Raw | 資料殘留、權限過寬 |
| Ephemeral | 資料遺失、殘留資料未清除、機密落地 |
| Long-term | 保存期間金鑰遺失或演算法過時、取回延遲、銷毀不徹底 |

通用威脅:未授權存取、資料外洩、勒索與惡意軟體、拒絕服務、資料殘留(remanence)、內部人員濫用。

### 名詞解釋

- **Snapshot**:某一時點的磁碟區副本,常是外洩來源。
- **Data remanence**:刪除後仍殘留的資料。
- **Bucket policy / ACL**:物件儲存的存取規則。
- **Immutable storage / WORM**:寫入後不可修改或刪除,適合稽核與勒索防護。

### 延伸知識:加密層次與儲存選型

#### 加密的位置

| 位置 | 誰加密 | 金鑰 | 特性 |
|---|---|---|---|
| 伺服器端加密(平台管理金鑰) | CSP | CSP 管理 | 最簡單,客戶控制最少 |
| 伺服器端加密(客戶管理金鑰) | CSP | 客戶在 KMS 管理 | 可撤銷、可稽核 |
| 客戶端加密 | 客戶在上傳前 | 客戶保管 | CSP 看不到明文,客戶責任最大 |

#### 備份、快照、複寫、封存的差別

| 項目 | 目的 | 注意 |
|---|---|---|
| 快照 | 某時點的磁碟區副本,快速回復 | 常是外洩來源,要加密與限權 |
| 備份 | 資料遺失後復原 | 要隔離、加密、測試還原 |
| 複寫 | 提高可用性 | 錯誤與勒索也會同步複寫 |
| 封存 | 長期低成本保存 | 不可變、金鑰長期保存 |

#### 選型

- 靜態網站與備份:物件。資料庫與作業系統:磁碟區。暫存與快取:暫態。長期合規:封存。

### 情境演練

安全團隊發現某 bucket 對全網公開,裡面有客戶資料。**處置順序**:先立刻限制存取並保全存取記錄,再評估外洩範圍與通報義務,最後改善政策(預設封鎖公開存取)。

### 考點與陷阱

> Tip:物件儲存最常見的風險是**權限設定錯誤**,不是硬體層攻擊。

> 陷阱:暫態儲存不能放唯一副本;實例結束資料就沒了。

## 2.3 設計與應用資料安全技術與策略
<!-- covers: 1,2,3,4,5,6 -->

> 一句話:加密保護機密、雜湊保護完整、遮罩與代碼化降低暴露、DLP 擋外流、金鑰與機密管理決定一切成敗。

### 白話重點

#### 加密與金鑰管理

- **對稱加密**:同一把金鑰加解密,快,適合大量資料。
- **非對稱加密**:公鑰與私鑰,用於金鑰交換與簽章。
- **信封加密(envelope encryption)**:用資料金鑰(DEK)加密資料,再用主金鑰(KEK)加密 DEK。好處:輪替主金鑰不用重新加密所有資料。
- **KMS**:雲端金鑰管理服務;**HSM**:硬體保管金鑰。
- **金鑰控制模型**:CSP 管理、客戶管理(BYOK)、客戶保管(HYOK)。
- **金鑰與資料分開保管**,並有輪替、備份、撤銷、銷毀程序與稽核。

#### 雜湊

- 單向、固定長度輸出,用來驗證**完整性**。
- **不可否認性**需要數位簽章(雜湊再用私鑰簽署)與身分綁定,單靠雜湊不夠。

#### 資料混淆(obfuscation)

| 技術 | 可否還原 | 說明 |
|---|---|---|
| 靜態遮罩(static masking) | 否 | 產生不可還原的測試資料副本 |
| 動態遮罩(dynamic masking) | 原值不變 | 依使用者權限即時遮蔽顯示 |
| 匿名化(anonymization) | 否 | 無法再識別個人 |
| 假名化(pseudonymization) | 可(用額外資訊) | 在 GDPR 下仍屬個資 |

#### 代碼化(tokenization)

- 用沒有意義的 token 取代敏感值,對照表存在安全的 **token vault**。
- 授權流程可用 token 取回原值。
- 常用於縮小 PCI DSS 範圍:大多數系統只處理 token,不接觸卡號。
- 與加密不同:token 與原值**沒有數學關係**。

#### DLP

- 偵測並阻擋敏感資料外流。位置:端點、網路、儲存、雲端應用。
- 依賴**資料分類與標籤**,否則誤報與漏報都多。

#### 金鑰、機密與憑證管理

- **機密(secrets)**:API 金鑰、密碼、token。使用保險庫(vault),不放程式碼與設定檔。
- **短期憑證**與**自動輪替**。
- **憑證**要管理生命週期:簽發、更新、撤銷、過期監控。

### 比較表:Tokenization vs Encryption vs Hashing vs Masking

| 技術 | 可取回原值 | 數學關係 | 典型用途 |
|---|---|---|---|
| Encryption | 是(用金鑰) | 有 | 機密性 |
| Tokenization | 是(用 vault) | 無 | 縮小合規範圍 |
| Hashing | 否 | 單向 | 完整性、密碼儲存 |
| Masking | 看類型 | 無 | 測試資料、顯示 |

### 名詞解釋

- **DEK / KEK**:資料加密金鑰 / 金鑰加密金鑰。
- **BYOK / HYOK**:自帶金鑰 / 金鑰只存在客戶端。
- **Salt**:雜湊密碼時加入的隨機值,防彩虹表。
- **Key rotation**:定期更換金鑰。

### 考點與陷阱

> Tip:要降低系統接觸卡號的範圍、又要能對授權流程取回原值,答 tokenization。

> 陷阱:匿名化與假名化不同;假名化後的資料仍可能是個資。

> 陷阱:加密再強,金鑰管理不當就沒有意義(例如金鑰與資料放在同一個 bucket)。

## 2.4 實作資料探索
<!-- covers: 1,2,3,4 -->

> 一句話:不知道資料在哪就保護不了。探索是分類、保護與合規的起點。

### 白話重點

| 資料類型 | 說明 | 探索難度與方法 |
|---|---|---|
| 結構化 | 有固定綱要,如關聯式資料庫 | 容易:欄位與結構明確,掃描綱要與內容 |
| 半結構化 | 有標籤或鍵值但綱要彈性,如 JSON、XML、日誌 | 中等:要解析內容與鍵名 |
| 非結構化 | 文件、郵件、影像、影音 | 困難:靠內容掃描、模式比對、ML 分類 |

- **資料位置**:要掌握資料在哪些區域、帳號、服務、備份與第三方 SaaS 內。
- **雲端探索工具**:自動掃描 bucket、資料庫與 SaaS 中的敏感資料。
- 探索結果餵給**分類、DLP、合規報告**。
- 探索要持續進行,不是一次性:雲端資料不斷新增與搬移。

### 名詞解釋

- **Shadow data**:無人知道或無人管理的資料副本。
- **Pattern matching / regex**:以格式辨識(如卡號、身分證字號)。
- **Data catalog**:資料目錄,記錄資料集、擁有者與位置。

### 延伸知識:探索怎麼做

#### 常見探索方法

| 方法 | 說明 | 適合 |
|---|---|---|
| 內容分析(content analysis) | 以規則運算式、字典、檢查碼辨識卡號、身分證字號 | 結構化與半結構化 |
| 中繼資料分析 | 看檔名、擁有者、建立時間、標籤 | 初篩,快速 |
| 標籤式 | 依既有標籤與分類 | 已有治理的環境 |
| 機器學習分類 | 對非結構化內容判斷類型與敏感度 | 文件、影像、郵件 |

#### 雲端特有挑戰

- 資料散落在多帳號、多區域、多服務與 SaaS。
- 加密資料要有金鑰才能掃描。
- 探索工具本身需要讀取權限,要最小權限並監控。
- 暫態資料(容器、無伺服器)要在產生處或集中日誌探索。
- 掃描會產生成本與效能影響。

#### 探索結果怎麼用

1. 建立資料清冊(data inventory)。
2. 對應法規與分類。
3. 決定保護措施(加密、存取、DLP)。
4. 清理多餘資料(資料最小化)。

### 情境演練

合規稽核要求證明「所有含個資的資料都有加密」。團隊先做資料探索,發現開發環境有未登記的資料庫副本含真實個資。**重點**:探索先於保護;沒有探索就無法證明涵蓋範圍。

### 考點與陷阱

> Tip:欄位不一致的 JSON 或 XML 檔,答半結構化。

> 陷阱:日誌的分類取決於格式。有鍵值的記錄屬半結構化;純文字訊息偏非結構化。答題以題目描述為準。

## 2.5 規劃與實作資料分類
<!-- covers: 1,2,3 -->

> 一句話:分類決定保護的強度。先分類,再對應控制。

### 白話重點

- **分類政策(classification policy)**:定義等級(例如公開、內部、機密、受限)、判定準則(依敏感度、法規、商業價值)、各等級的處理要求(加密、存取、保存、傳輸)與負責人。
- **資料對應(data mapping)**:資料存在哪、誰擁有、如何流動、經過哪些系統與第三方。
- **標籤與標記(labeling and tagging)**:把分類寫進中繼資料,驅動自動化控制(加密、DLP、存取政策)。
  - 標籤要有治理:誰能改、改了要記錄,否則可被任意竄改。
  - 雲端資源標籤也用於成本與環境區分。
- **分類由 data owner 決定**;custodian 負責執行。
- **彙整資料**的敏感度可能高於個別資料(聚合效應)。

### 名詞解釋

- **Data owner**:對資料分類與使用負責。
- **Data custodian**:執行日常保護(備份、存取)。
- **Sensitivity vs Criticality**:敏感度是外洩的衝擊;關鍵性是遺失或中斷的衝擊。
- **Aggregation**:多筆低敏感資料組合後變成高敏感。

### 延伸知識:分類等級與處理要求(範例)

| 等級 | 例子 | 加密 | 存取 | 傳輸 | 銷毀 |
|---|---|---|---|---|---|
| 公開 | 行銷網站內容 | 不強制 | 無限制 | 可公開 | 一般刪除 |
| 內部 | 內部公告 | 建議 | 全體員工 | 內部網路 | 一般刪除 |
| 機密 | 客戶資料、合約 | 必須 | 需要知道才能存取 | 加密傳輸 | 加密抹除 |
| 受限 | 金鑰、個資大量檔 | 必須且強控制 | 嚴格審核、記錄 | 專線或端對端加密 | 可驗證銷毀 |

- 等級名稱各組織不同,考試看**邏輯**:等級越高,控制越嚴。
- **分類要素**:機密性影響、法規要求、商業價值、重要性。
- **重新分類與降級**:資料敏感度會隨時間改變(例如財報公布後),要有流程與責任人。
- **標籤方式**:檔案標頭、中繼資料、雲端資源標籤、資料庫欄位標記。
- **聚合**:多筆低敏感資料彙整後可能升級。

### 情境演練

兩個部門對同一份資料各自分類成「內部」與「機密」。**解法**:由資料擁有者(data owner)依政策裁定,並記錄;不是取較低或自行平均。

### 考點與陷阱

> Tip:「誰決定這份資料的分類?」答 data owner。

> 陷阱:標籤本身沒有保護效果,必須搭配依標籤執行的控制。

## 2.6 設計與實作資訊權限管理(IRM)
<!-- covers: 1,2 -->

> 一句話:IRM 讓保護「跟著資料走」,即使檔案離開你的系統也能控制與撤銷。

### 白話重點

#### 目標

| 目標 | 說明 |
|---|---|
| 資料權利(data rights) | 能讀取、列印、複製、轉寄、編輯、有效期限 |
| 授權發放(provisioning) | 誰在什麼條件下取得什麼權利 |
| 存取模型(access models) | 角色式(RBAC)、屬性式(ABAC)、身分式、聲明式 |

#### 工具:憑證的簽發與撤銷

- IRM 通常依靠 **PKI**:為使用者與文件簽發憑證與授權。
- **撤銷**:CRL(憑證撤銷清單)、OCSP(線上憑證狀態協定)。
- 離線使用時,撤銷可能延遲(快取)。

#### 挑戰

- 跨組織互通、使用者體驗、離線使用、效能、與各種格式相容。

### 比較表:IRM vs DLP vs DRM

| 技術 | 保護方式 | 重點 |
|---|---|---|
| IRM | 保護檔案本身,權限隨檔案 | 可在檔案已下載後撤銷 |
| DLP | 偵測與阻擋資料外流 | 在邊界或端點 |
| DRM | 保護數位內容的著作權使用 | 偏消費性內容 |

### 名詞解釋

- **PKI**:公開金鑰基礎建設。
- **CRL / OCSP**:撤銷清單 / 即時狀態查詢。
- **Entitlement**:被授予的權利。

### 延伸知識:IRM 如何運作與限制

#### 典型流程

1. 作者在文件上設定**權利**:誰可讀、列印、複製、轉寄、有效期限。
2. 文件被加密,**權利資訊**與**內容金鑰**交給 IRM 服務(或嵌入並用公鑰保護)。
3. 讀者開啟時,用戶端向 IRM 服務**驗證身分**並取得授權;符合權利才解密。
4. 作者可隨時**撤銷**或修改權利;離線快取到期後需重新授權。

#### 優點與限制

| 優點 | 限制 |
|---|---|
| 保護隨檔案走,離開組織後仍有效 | 需要用戶端或相容應用 |
| 可撤銷、可記錄誰開過 | 螢幕截圖、拍照等「類比漏洞」難防 |
| 與分類標籤整合,自動套用 | 跨組織互通與格式支援不一 |
| 可設定有效期限 | 離線時撤銷延遲 |

- **與 DLP 搭配**:DLP 在邊界攔截;IRM 保護已出去的檔案。

### 情境演練

合作夥伴合約結束,公司希望之前分享的設計檔無法再開啟。**可行**:若檔案在分享時已套用 IRM,撤銷該夥伴的授權即可;**不可行**:若只是用雲端分享連結傳送且檔案已被下載,僅靠 DLP 無法追回。

### 考點與陷阱

> Tip:「檔案已被合作夥伴下載,仍要能撤銷開啟權」,答 IRM。

> 陷阱:憑證本身不等於不可否認性,不可否認性還需要簽章、金鑰保管與記錄。

## 2.7 規劃與實作資料保存、刪除與封存政策
<!-- covers: 1,2,3,4 -->

> 一句話:保存多久、怎麼刪、怎麼存、什麼時候不能刪,都要事先定義並可驗證。

### 白話重點

#### 保存政策(retention)

- 定義每類資料的**最短與最長保存期限**、法規或合約依據、起算點、責任人。
- 最短保存來自法規與業務需求;最長保存常來自隱私要求(資料最小化)。

#### 刪除程序與機制

| 方式 | 說明 | 雲端注意 |
|---|---|---|
| 邏輯刪除 | 只移除指標或標記 | 資料仍可能殘留 |
| 軟刪除 | 放進回收區,可復原 | 超過期限才真正刪除 |
| 覆寫 | 以隨機資料覆蓋 | 雲端多副本難以保證 |
| 加密抹除(crypto-shredding) | 銷毀金鑰 | 雲端首選,前提金鑰無其他副本 |
| 實體銷毀 | 粉碎、焚化 | 客戶通常無法執行 |

- 消磁(degauss)對 SSD 與快閃媒體不可靠。
- **備份、快照、複本、日誌**都要納入刪除範圍。

#### 封存(archiving)

- 低成本長期保存,存取頻率低。
- 常用 **WORM / 不可變儲存**。
- 封存不等於備份:備份是為了復原,封存是為了保存與合規。
- 長期保存要考慮:金鑰的長期保存、格式的可讀性、完整性驗證。

#### 法律保全(legal hold)

- 因訴訟或調查,**暫停**相關資料的刪除,並限制為授權人員存取。
- 要記錄保全範圍、時間、責任人。
- 與刪除權(例如 GDPR 第 17 條)衝突時,依法律義務暫停刪除,並與法務確認、記錄決策。

### 名詞解釋

- **Retention clock**:保存期限的起算點。
- **WORM**:Write Once Read Many。
- **Legal hold / Litigation hold**:法律保全 / 訴訟保全。
- **Preservation order**:法院或監管機關的保全命令,不等同企業內部發出的 legal hold。

### 延伸知識:備份、封存與刪除驗證

#### 備份 vs 封存

| 項目 | 備份(backup) | 封存(archive) |
|---|---|---|
| 目的 | 資料遺失後復原 | 長期保存以供合規與查閱 |
| 存取頻率 | 平常不用,出事才用 | 偶爾查詢 |
| 保存期 | 較短,輪替 | 長,依法規 |
| 資料狀態 | 近期副本 | 通常是已完成的資料 |
| 可變性 | 可覆蓋、輪替 | 常為不可變(WORM) |

#### 刪除要留下證據

- 刪除請求與核准紀錄、範圍清單、執行時間、執行者。
- 加密抹除要記錄金鑰銷毀事件與**確認無其他副本**。
- 對 CSP:要求刪除證明、確認副本與備份的刪除期限。

#### 保存排程範例

| 資料類型 | 最短 | 最長 | 依據 |
|---|---|---|---|
| 財務會計憑證 | 依法規年限 | 到期後處置 | 稅務與會計法規 |
| 客戶個資 | 業務關係存續期 | 目的達成即刪 | 隱私法(資料最小化) |
| 日誌 | 依稽核與鑑識需求 | 儲存成本與隱私 | 內部政策 |

> 待核對:各國實際保存年限依當地法規而不同,請以所在地法規為準。

### 情境演練

客戶退出服務後要求刪除資料,但該客戶恰是進行中訴訟的當事人。**正確處置**:先確認法律保全,範圍內資料暫停刪除並限制存取,其餘資料依政策刪除,並以書面向客戶說明例外。

### 考點與陷阱

> Tip:保全範圍內的資料,即使保存期限到期或收到刪除請求,也要先暫停刪除。

> 陷阱:只刪除主要副本,卻忘記備份、快照與複本。

## 2.8 設計與實作資料事件的可稽核性、可追溯性與問責
<!-- covers: 1,2,3 -->

> 一句話:每個重要資料事件都要能回答:誰、做了什麼、何時、從哪裡、結果如何,而且記錄本身可信。

### 白話重點

#### 事件來源與屬性

- 來源:應用、資料庫、儲存存取日誌、管理平面稽核日誌(如雲端活動記錄)、網路流量、IAM 事件。
- 必要屬性:**身分**(誰)、**動作**(做了什麼)、**對象**(哪筆資料)、**時間**(何時)、**來源位置**(IP、地理位置)、**結果**。

#### 記錄、儲存與分析

- **集中化**:送到獨立、不可竄改的位置(與被監控系統分離)。
- **保存期限**依法規與合約。
- **分析**:SIEM 關聯分析、警示、報表。
- **完整性保護**:雜湊鏈、簽章、寫入後不可修改。

#### 監管鏈與不可否認性

- **Chain of custody**:證據從取得到呈現,每次移交都有記錄(誰、何時、為何、狀態)。
- **不可否認性(non-repudiation)**需要:
  1. 唯一身分(不可共用帳號)。
  2. 防竄改記錄。
  3. **可信時間戳**(由受信任第三方簽發)。
  4. 數位簽章。

### 名詞解釋

- **Audit trail**:稽核軌跡。
- **Accountability**:能把行為歸屬到個人或實體。
- **Trusted timestamping**:由受信任的時間戳記機構簽發。
- **Tamper-evident**:被竄改能被察覺。

### 延伸知識:雲端各層的日誌與關聯

#### 日誌來源分層

| 層級 | 內容 | 價值 |
|---|---|---|
| 管理平面日誌 | 誰呼叫了哪些管理 API(建立、修改、刪除資源) | 追蹤設定變更與權限濫用 |
| 資料平面日誌 | 誰讀寫了哪個物件或資料表 | 資料存取稽核 |
| 網路流量日誌 | 來源、目的、埠、位元組(流量記錄) | 橫向移動、外洩偵測 |
| 身分日誌 | 登入、MFA、權限變更 | 帳號被盜 |
| 應用與資料庫日誌 | 業務操作 | 業務事件追溯 |

#### 日誌設計原則

- **5W1H**:誰(Who)、做什麼(What)、何時(When)、哪裡(Where)、為什麼或來源(Why)、如何(How)。
- **時間同步**:所有來源使用同一時間基準,否則關聯會失準。
- **保護日誌**:寫入後不可改、與被監控系統分離、存取受控、備份。
- **敏感資料遮蔽**:日誌本身不該寫入密碼、金鑰與完整卡號。
- **保存與成本平衡**:熱資料(近期)快速查詢,冷資料(長期)便宜存放。

### 情境演練

調查資料外洩時發現,管理員可以刪除自己帳號相關的日誌。**問題**:日誌缺乏獨立性與防竄改。**改善**:日誌送到獨立帳號的不可變儲存,管理員無刪除權,並對日誌存取本身再做稽核。

### 考點與陷阱

> Tip:共用管理員帳號會直接破壞問責與不可否認性。

> 陷阱:只做 NTP 時間同步不等於可信時間戳,後者由受信任第三方簽發。

## 2.9 理解 AI/ML 資料保護
<!-- covers: 1,2 -->

> 一句話:訓練資料與模型本身都是要保護的資產,風險在隱私外洩與資料被污染。

### 白話重點

#### 資料集與模型隱私

- **資料最小化**、去識別化、存取控制、同意與目的限定。
- **差分隱私(differential privacy)**:在資料或結果中加入受控的雜訊,使得無法判斷某個個體是否在資料集中。
- 主要風險:
  - **成員推論(membership inference)**:判斷某人資料是否在訓練集。
  - **模型反推(model inversion)**:從模型輸出推回訓練資料特徵。
  - **記憶化(memorization)**:模型逐字記住訓練資料(特別是大型語言模型)。

#### 資料集與模型安全

- **資料投毒(data poisoning)**:在訓練資料中植入惡意資料,改變模型行為。
- **供應鏈**:預訓練模型、第三方資料集的來源與完整性。
- **驗證與確認**:
  - Verification:確認資料與模型建置**符合規格**、未被竄改。
  - Validation:確認模型**符合預期用途**與績效。
- **控制**:來源驗證、版本與雜湊、存取控制、隔離訓練環境、監控模型輸出。

> 備註:ML 實務中 validation 與 verification 常被互相混用,答題以題目上下文為準。

### 名詞解釋

- **Differential privacy**:差分隱私。
- **Membership inference / Model inversion**:成員推論 / 模型反推。
- **Data provenance**:資料出處與歷程。
- **Training / Inference**:訓練 / 推論。

### 延伸知識:ML 生命週期與威脅對應

| 階段 | 主要威脅 | 控制 |
|---|---|---|
| 資料蒐集 | 來源不明、偏誤、授權問題 | 來源驗證、同意與授權檢查 |
| 資料準備 | 投毒、標記錯誤、個資殘留 | 去識別化、完整性檢查、版本管理 |
| 訓練 | 訓練環境遭入侵、竊取資料 | 隔離環境、最小權限、記錄 |
| 部署 | 模型被竊取或替換 | 簽署、存取控制、完整性驗證 |
| 推論 | 成員推論、模型反推、提示詞注入、資訊洩漏 | 差分隱私、輸出過濾、速率限制、監控 |

#### 生成式 AI 的資料保護

- **RAG(檢索增強生成)**:模型從向量資料庫取回文件。要對**文件層級做存取控制**,否則使用者可能透過模型看到無權查看的內容。
- **向量與嵌入(embeddings)**:可能被反推回原文,要當成敏感資料保護。
- **提示詞與輸出紀錄**:可能含個資,日誌要遮蔽與限存期限。

### 情境演練

公司把內部文件接到聊天助理,員工問到薪資表內容時助理照答。**根因**:檢索層沒有套用文件的存取權限。**修正**:查詢時以使用者身分過濾文件、對敏感類別排除或遮蔽。

### 考點與陷阱

> Tip:要降低攻擊者判斷「某人資料是否在訓練集」的風險,答差分隱私與資料最小化。

> 陷阱:只加密模型檔案不處理推論時的洩漏;靜態加密防的是檔案被偷,不是查詢時的資訊洩漏。
