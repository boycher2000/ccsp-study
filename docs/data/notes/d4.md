## 4.1 倡導應用程式安全訓練與意識
<!-- covers: 1,2,3 -->

> 一句話:多數應用程式漏洞來自可預防的錯誤。訓練開發者認得常見漏洞清單,是成本最低的防線。

### 白話重點

#### 雲端開發基礎

- **API 優先**、**託管服務**、**基礎設施即程式碼(IaC)**、**暫態與不可變部署**、**微服務與容器**。
- 開發者要理解**共同責任**:應用層的安全永遠是客戶的。
- 機密不放程式碼與設定檔,用保險庫與短期憑證。

#### 常見陷阱

- 憑證寫死在程式碼或公開 repo。
- 權限過大(例如給 `*` 的 IAM 政策)。
- 錯誤設定(公開 bucket、預設密碼)。
- 為了速度跳過安全關卡。
- 信任第三方套件與映像,不驗證。
- 忽略輸入驗證與輸出編碼。

#### 常見雲端漏洞清單

| 清單 | 內容與用途 |
|---|---|
| OWASP Top 10 | 網頁應用最常見的風險類別 |
| OWASP ASVS | **應用程式安全驗證標準**,分驗證等級,用來設計、建置與測試 |
| OWASP API Security Top 10 | API 特有風險,如 BOLA(物件層級授權失效) |
| OWASP Top 10 for LLM Applications | 大型語言模型應用的風險 |
| CWE Top 25(大綱寫 SANS Top 25) | 最危險的軟體弱點排行,現由 MITRE 發布 |

**OWASP Top 10:2025(官方頁面)**

1. A01 Broken Access Control
2. A02 Security Misconfiguration
3. A03 Software Supply Chain Failures
4. A04 Cryptographic Failures
5. A05 Injection
6. A06 Insecure Design
7. A07 Authentication Failures
8. A08 Software or Data Integrity Failures
9. A09 Security Logging and Alerting Failures
10. A10 Mishandling of Exceptional Conditions

**OWASP Top 10 for LLM Applications(2025)**

1. LLM01 Prompt Injection
2. LLM02 Sensitive Information Disclosure
3. LLM03 Supply Chain
4. LLM04 Data and Model Poisoning
5. LLM05 Improper Output Handling
6. LLM06 Excessive Agency
7. LLM07 System Prompt Leakage
8. LLM08 Vector and Embedding Weaknesses
9. LLM09 Misinformation
10. LLM10 Unbounded Consumption

> 待核對:大綱只寫「OWASP Top-10」,沒指定年份,考試以哪一版為準未確認。2021 版的 SSRF 在 2025 版不再單獨列出;官方首頁未說明併入哪一項,二手來源稱併入 A01,請以 OWASP 官方文件為準。

> 待核對:OWASP API Security Top 10 的最新版次與項目順序,請對照 owasp.org。

### 名詞解釋

- **BOLA**:Broken Object Level Authorization,可存取他人的物件。
- **ASVS**:Application Security Verification Standard。
- **Prompt injection**:以輸入操縱模型行為。
- **CWE**:Common Weakness Enumeration,弱點類型編號系統。

### 考點與陷阱

> Tip:看到「驗證標準、分等級、用來檢查應用程式」,想 ASVS。

> 陷阱:Top 10 是風險類別清單,不是完整的測試標準;ASVS 才是可驗證的要求清單。

## 4.2 描述安全軟體開發生命週期
<!-- covers: 1,2 -->

> 一句話:安全要在每個階段都有活動,而且從業務需求開始。

### 白話重點

#### 業務需求

- 業務需求驅動安全需求:資料分類、法規、SLA、風險胃納。
- 安全需求要可測試、可驗證。
- 區分**功能需求**、**非功能需求**(效能、可用性、安全性)與**安全需求**。

#### 階段

| 階段 | 安全活動 |
|---|---|
| 需求 | 安全與隱私需求、濫用案例 |
| 設計 | 威脅建模、安全設計審查 |
| 撰寫(code) | 安全編碼、同儕審查、SAST |
| 測試 | DAST、IAST、SCA、滲透測試 |
| 部署 | 強化、組態檢查、簽署 |
| 維護 | 修補、監控、事件回應、停用 |

#### 方法論

| 方法 | 特色 | 安全風險 |
|---|---|---|
| 瀑布(waterfall) | 階段循序,前一階段完成才進入下一階段 | 問題常在後期才發現,修正成本高 |
| 敏捷(agile) | 迭代與衝刺,持續交付 | 安全要融入每個迭代,否則被當成負擔 |
| DevOps / DevSecOps | 開發與營運整合,安全自動化進管線 | 管線本身成為攻擊目標 |

### 名詞解釋

- **Shift-left**:把安全活動往前移到早期階段。
- **Sprint**:敏捷的固定週期迭代。
- **Definition of Done**:完成的標準,可加入安全要求。
- **Abuse case**:從攻擊者角度描述的使用情境。

### 延伸知識:開發模型與 DevSecOps 管線

#### 常見模型

| 模型 | 特色 | 安全重點 |
|---|---|---|
| 瀑布 | 階段循序,文件多 | 需求與設計階段就要寫好安全需求 |
| 螺旋(spiral) | 每圈做風險分析再迭代 | 每圈都有風險評估,適合高風險專案 |
| V 模型 | 每個開發階段對應一個測試階段 | 需求對驗收、設計對整合測試 |
| 敏捷 | 短週期、可用成果漸進交付 | 把安全放進 backlog 與完成定義 |
| DevOps | 開發與營運一體,頻繁部署 | 安全自動化進 CI/CD |

#### DevSecOps 管線的安全活動

| 管線階段 | 安全活動 |
|---|---|
| 提交前 | 機密掃描、pre-commit 檢查、IDE 外掛 |
| 建置 | SAST、SCA、映像掃描、SBOM 產生、簽署成品 |
| 測試 | DAST、IAST、API 測試、基礎設施即程式碼掃描 |
| 部署 | 準入控制、組態驗證、金絲雀部署 |
| 營運 | 監控、WAF/RASP、弱點管理、事件回應 |

#### 需求的種類

- **功能需求**:系統要做什麼。
- **非功能需求**:效能、可用性、可維護性、**安全性**。
- **安全需求**:機密性、完整性、可用性、驗證、授權、稽核、隱私。要**可測試、可追溯**。

### 情境演練

團隊以兩週衝刺交付,安全測試被排在「最後一個衝刺」,結果多次被擠掉。**改善**:把安全需求寫進使用者故事與完成定義(DoD),把 SAST、SCA 放進每次提交的管線。

### 考點與陷阱

> Tip:降低後期重工的方法,是把安全需求與設計審查往前移(shift-left)。

> 陷阱:Secure SDLC 的核心是 CIA 與隱私,不是單純功能完整;別把 safety(人身安全)與 CIA 混為一談。

## 4.3 應用安全 SDLC
<!-- covers: 1,2,3,4,5 -->

> 一句話:把雲端特有風險放進設計,用威脅建模找出問題,用安全編碼與組態管理防止錯誤。

### 白話重點

#### 雲端特有風險

| 風險 | 說明 | 對應 |
|---|---|---|
| 共享技術問題 | 多租戶、hypervisor、共享元件 | 隔離設計、客戶管理金鑰 |
| CSP 內部人員威脅 | 供應商人員可能存取資料 | 加密、客戶管理金鑰、合約與稽核 |
| 缺乏可視性與控制 | 看不到底層 | 應用層日誌與追蹤、API 稽核 |
| 法律與管轄權 | 資料落地與跨境 | 區域限制、合約、功能閘控 |

#### 威脅建模

| 方法 | 內容 |
|---|---|
| **STRIDE** | Spoofing、Tampering、Repudiation、Information disclosure、Denial of service、Elevation of privilege |
| **DREAD** | 風險評分:Damage、Reproducibility、Exploitability、Affected users、Discoverability |
| **ATASM** | Architecture、Threats、Attack surfaces、Mitigations |
| **PASTA** | 風險導向,七個階段 |

PASTA 七階段:定義目標 → 定義技術範圍 → 應用分解 → 威脅分析 → 弱點與缺陷分析 → 攻擊建模 → 風險與衝擊分析。

> 口訣:**STRIDE 找威脅類型、DREAD 打分數、ATASM 走流程、PASTA 七步看風險**。

#### 避免常見漏洞與安全編碼

- 輸入驗證、輸出編碼、參數化查詢、最小權限、安全預設、錯誤處理不洩漏資訊。
- **OWASP ASVS**:驗證要求清單。
- **SAFECode**:軟體保證論壇提供的安全開發實務指引。

#### 軟體組態管理與版本控制

- 所有程式碼、設定、IaC 納入版本控制。
- 變更可追溯、可審查、可回復;分支保護、簽署提交。
- 組態漂移要偵測。

### 名詞解釋

- **Attack surface**:攻擊面。
- **Parameterized query**:參數化查詢,防 SQL 注入。
- **Configuration drift**:實際組態與基準不一致。
- **Code signing**:程式碼簽署。

### 延伸知識:威脅建模怎麼做

#### STRIDE 對應的安全屬性與常見控制

| 威脅 | 破壞的屬性 | 常見控制 |
|---|---|---|
| Spoofing 偽冒 | 驗證 | 強驗證、MFA、憑證 |
| Tampering 竄改 | 完整性 | 簽章、雜湊、存取控制 |
| Repudiation 否認 | 不可否認性 | 稽核日誌、簽章、可信時間戳 |
| Information disclosure 資訊洩漏 | 機密性 | 加密、存取控制、遮罩 |
| Denial of service 阻斷服務 | 可用性 | 速率限制、備援、彈性擴充 |
| Elevation of privilege 權限提升 | 授權 | 最小權限、職務分離、輸入驗證 |

#### 威脅建模流程(通用)

1. **定義範圍與目標**:要保護什麼、信任邊界在哪。
2. **畫架構圖**:資料流圖(DFD)標出元件、資料流、儲存、信任邊界。
3. **辨識威脅**:對每個元件與資料流套用 STRIDE。
4. **評估風險**:DREAD 或其他評分(DREAD 常被批評過於主觀)。
5. **規劃緩解**:控制措施並指定負責人。
6. **驗證**:測試與審查,隨架構變更更新。

- **何時做**:設計階段最划算,重大變更時重做。
- **雲端要特別畫出**:跨租戶邊界、跨帳號、跨區域、第三方 API、管理平面。

### 情境演練

新功能讓使用者上傳檔案,並由背景服務處理。威脅建模辨識:檔案內容可能含惡意程式(Tampering)、檔名造成路徑穿越(Elevation of privilege)、大量上傳耗盡資源(DoS)。**對應**:檔案類型驗證與掃描、隔離處理環境、大小與速率限制。

### 考點與陷阱

> Tip:「風險導向、七個階段」答 PASTA。

> 陷阱:自訂客戶管理金鑰降低 CSP 內部人員風險,但不能完全消除:資料在使用中時仍可能被存取。

## 4.4 應用雲端軟體保證與驗證
<!-- covers: 1,2,3,4 -->

> 一句話:用多種測試方法在管線中不同位置驗證功能與安全,並以濫用案例補足。

### 白話重點

#### 功能性與非功能性測試

- **功能性**:是否符合需求(單元、整合、系統、驗收)。
- **非功能性**:效能、負載、可用性、相容性、**安全性**。
- **CI/CD**:在管線設自動化測試與安全關卡,失敗就阻擋。

#### 安全測試方法

| 方法 | 執行方式 | 優點 | 限制 |
|---|---|---|---|
| 黑箱(blackbox) | 不知內部,從外部測 | 接近真實攻擊者 | 覆蓋率不足 |
| 白箱(whitebox) | 可看原始碼與架構 | 覆蓋率高 | 需要資源與技能 |
| **SAST** | 靜態分析原始碼,不執行 | 早期、可進 IDE 與 CI | 誤報多、看不到執行期問題 |
| **DAST** | 對執行中的應用外部攻擊式測試 | 找出執行期漏洞 | 需要可執行環境、晚期 |
| **IAST** | 在應用內放探針,測試時於執行期觀察 | 精準、含程式碼位置 | 需要整合與測試覆蓋 |
| **SCA** | 分析第三方元件的已知漏洞與授權 | 供應鏈風險 | 只能找已知問題 |

> 口訣:**S 靜、D 動、I 互(探針)、SCA 看元件**。

#### QA 與濫用案例

- **QA**:流程與品質,不等於安全測試,也不等於滲透測試。
- **濫用案例測試**:從攻擊者角度設計情境(例如繞過驗證、篡改價格),補足一般功能測試。

### 名詞解釋

- **False positive / negative**:誤報 / 漏報。
- **Fuzzing**:丟入大量隨機或畸形輸入找崩潰與漏洞。
- **Regression test**:回歸測試。
- **Instrumentation**:在程式中插入探針。

### 延伸知識:測試放在管線的哪裡

| 時機 | 適合的測試 | 為什麼 |
|---|---|---|
| 撰寫中 | IDE 外掛、SAST | 最早、成本最低 |
| 提交與建置 | SAST、SCA、機密掃描、映像掃描 | 自動化、快速反饋 |
| 整合測試環境 | DAST、IAST、API 測試 | 需要執行中的應用 |
| 預備環境(staging) | 滲透測試、模糊測試(fuzzing) | 接近正式環境 |
| 正式環境 | 監控、RASP、紅隊演練、漏洞賞金 | 真實流量與環境差異 |

- **模糊測試(fuzzing)**:丟入大量隨機或畸形輸入找崩潰與漏洞,不屬 SAST 或 DAST 的單純分類,常與兩者並用。
- **滲透測試**:人工、目標導向,與自動化 DAST 互補。
- **指標**:缺陷密度、發現時間、修補時間、誤報率、覆蓋率。
- **功能測試層次**:單元 → 整合 → 系統 → 驗收;**回歸測試**確保修改沒破壞既有功能。

### 情境演練

SAST 報告 500 筆發現,開發者因誤報多而忽略。**改善**:依嚴重度與可利用性排序、調校規則、整合到 pull request 並只阻擋高風險,再用 IAST 或 DAST 交叉驗證。

### 考點與陷阱

> Tip:不執行程式、掃描原始碼,答 SAST;要在應用執行中觀察,答 DAST 或 IAST。

> 陷阱:IAST 屬於執行期分析,不是靜態;它結合應用內部資訊,但需要應用在測試中被執行。

## 4.5 使用經驗證的安全軟體
<!-- covers: 1,2,3,4 -->

> 一句話:你用的每一個函式庫、映像與供應商,都是你的攻擊面。要驗證來源、完整性、授權與維護狀態。

### 白話重點

#### 保護 API

- 驗證與授權(每個請求都要檢查,包含物件層級)。
- 速率限制、配額、輸入驗證、結構驗證、TLS。
- API 清單管理,避免影子 API。
- 回應不洩漏多餘資訊。
- 防範 BOLA、SSRF。

#### 供應鏈管理

| 面向 | 做法 |
|---|---|
| 供應商評估 | 問卷、稽核報告、滲透測試、安全開發流程 |
| 完整性(integrity) | 雜湊、簽章,確認內容沒被改過 |
| 真實性(authenticity) | 確認來源是宣稱的那個人,簽署與出處證明 |
| 授權(licensing) | 開源授權相容性與義務(授權風險屬供應鏈範圍,不只是法務問題) |

- **SBOM**(軟體物料清單):列出所有元件與版本,漏洞出現時能快速查詢。

#### 第三方軟體管理

- 清單、更新與弱點追蹤、合約要求(通報漏洞、支援期限)、退出計畫。

#### 經驗證的開源軟體

- 從受信任來源取得、固定版本、驗證簽章或雜湊。
- SCA 掃描、審查維護狀況與社群活躍度、內部鏡像儲存庫。

### 名詞解釋

- **SBOM**:Software Bill of Materials。
- **Provenance**:出處證明。
- **Typosquatting**:用近似名稱的惡意套件誘騙下載。
- **Dependency pinning**:固定相依套件版本。

### 延伸知識:API 與供應鏈控制清單

#### API 安全清單

- **驗證**:每個請求都要驗證(OAuth 2.0 的存取權杖、mTLS 等)。
- **授權**:**物件層級**與**功能層級**都要檢查,避免 BOLA。
- **輸入與結構驗證**:定義明確的結構,拒絕多餘欄位(防質量賦值)。
- **速率限制與配額**:防濫用與資源耗盡。
- **傳輸加密**:一律 TLS。
- **清單管理**:避免影子 API 與舊版本遺留。
- **回應最小化**:不回傳多餘欄位與詳細錯誤。
- **日誌與監控**:誰呼叫了什麼。

#### 供應鏈攻擊手法

| 手法 | 說明 |
|---|---|
| Typosquatting | 用相近名稱的惡意套件誘騙下載 |
| Dependency confusion | 內部套件名稱被公開儲存庫同名套件取代 |
| 惡意維護者或帳號被盜 | 合法套件被植入惡意程式 |
| 建置系統被入侵 | 成品在建置時被竄改 |

#### 防護

- **固定版本與鎖檔**、**私有鏡像儲存庫**、**簽章驗證**、**SBOM**(常見格式:SPDX、CycloneDX)、**SCA 掃描**、**最小相依**。

### 情境演練

安全團隊收到通報:某熱門開源函式庫發布了含惡意程式的新版本。**回應**:用 SBOM 查出受影響的服務,鎖定在前一個安全版本,輪替可能外洩的機密,並檢視建置與部署日誌。

### 考點與陷阱

> Tip:使用開源函式庫,先驗證簽章或雜湊,並用 SCA 掃描,而不是看熱門程度。

> 陷阱:簽章能證明真實性與完整性,但不證明軟體沒有漏洞。

## 4.6 理解並應用雲端應用架構特性
<!-- covers: 1,2,3,4 -->

> 一句話:在應用架構中加上 WAF、DAM、API gateway 等補充元件,並正確使用加密、沙箱與容器編排。

### 白話重點

#### 補充安全元件

| 元件 | 做什麼 | 注意 |
|---|---|---|
| WAF | 第 7 層 HTTP 過濾,防 SQL 注入、XSS | 規則要調校;不取代安全編碼 |
| DAM | 監控與記錄資料庫活動、警示異常 | 不加密、不取代 IAM |
| XML 防火牆 | 檢查 XML 流量(SOAP 等) | XXE 與 entity expansion 是不同攻擊 |
| API gateway | 驗證、授權、速率限制、路由 | 政策集中管理 |
| 負載平衡器 | 分流、TLS 終止、健康檢查 | 不是授權引擎 |

#### 密碼學

- 分層使用:傳輸(TLS)、靜態(儲存加密)、應用層(欄位加密)。
- 妥善管理金鑰;避免自創演算法。

#### 沙箱(sandboxing)

- 在受限環境執行不受信任的程式碼,限制檔案、網路、系統呼叫。
- 比較:沙箱 < 容器 < VM 的隔離強度(一般而言,取決於實作)。

#### 應用虛擬化與編排

| 技術 | 重點 |
|---|---|
| 微服務 | 拆小服務,攻擊面變多;服務間要驗證與授權 |
| 容器、Docker | 映像掃描、最小映像、非 root、唯讀檔案系統 |
| Kubernetes | RBAC、網路政策、準入控制、機密管理、控制平面保護 |

### 名詞解釋

- **XXE**:XML External Entity。
- **Entity expansion**:實體膨脹(如 billion laughs),耗盡資源。
- **TLS termination**:在負載平衡器解開 TLS。
- **Admission controller**:Kubernetes 在資源建立前的檢查機制。

### 延伸知識:容器與 Kubernetes 的安全層

#### 4C 模型(Kubernetes 文件)

| 層 | 內容 |
|---|---|
| Cloud(雲端) | 底層雲端帳號、網路、IAM |
| Cluster(叢集) | 控制平面、節點、RBAC、網路政策、稽核 |
| Container(容器) | 映像、執行環境、權限、機密 |
| Code(程式碼) | 應用本身的漏洞與相依 |

> 口訣:**每一層都依賴外層的安全:外層不安全,內層再好也沒用。**

#### 容器安全要點

- **映像**:使用最小基礎映像、固定標籤與摘要、掃描漏洞、簽署。
- **執行期**:非 root、唯讀檔案系統、移除不必要能力(capabilities)、限制資源。
- **機密**:不放映像與環境變數,用機密管理服務。
- **網路**:預設拒絕的網路政策,服務間只開必要通訊。

#### 服務網格(service mesh)

- 在服務之間提供 **mTLS**(雙向驗證加密)、政策、可觀測性,不必改應用程式碼。

#### 沙箱的層次

| 技術 | 隔離方式 |
|---|---|
| 作業系統層沙箱 | 限制系統呼叫與檔案存取 |
| 容器 | 命名空間與 cgroup,共享核心 |
| microVM / 沙箱執行環境 | 較強的隔離,啟動仍快 |
| VM | hypervisor 層隔離 |

### 情境演練

安全稽核發現多個 Pod 以 root 執行、可掛載主機路徑。**修正**:啟用 Pod 安全準入政策、禁止特權容器、限制 hostPath、使用非 root 使用者並採用唯讀根檔案系統。

### 考點與陷阱

> Tip:保護網頁免受 SQL 注入,答 WAF;監看資料庫查詢行為,答 DAM。

> 陷阱:負載平衡器終止 TLS 後,後端的內部流量仍要保護。

## 4.7 設計適當的 IAM 解決方案
<!-- covers: 1,2,3,4,5,6 -->

> 一句話:雲端安全的新邊界是身分。用聯邦與 SSO 集中管理,用 MFA 提高強度,用 CASB 補足可視性。

### 白話重點

#### 聯邦身分、IdP、SSO

- **聯邦身分**:跨組織信任同一個身分來源。
- **IdP(Identity Provider)**:發行並斷言身分。
- **SP / RP(Service Provider / Relying Party)**:依賴 IdP 的服務。
- **SSO**:一次驗證,多處使用;同時集中風險,IdP 失守就是全部失守。

| 協定 | 用途 |
|---|---|
| SAML 2.0 | 企業 SSO,以 XML 斷言 |
| OAuth 2.0 | **委派授權**(給第三方有限存取),本身不做驗證 |
| OpenID Connect(OIDC) | 建立在 OAuth 2.0 上的**驗證**層,以 ID token(JWT)傳身分 |

> 口訣:**OAuth 管「能做什麼」,OIDC 管「你是誰」**。

#### MFA

- 三類因子:**知道**(密碼)、**擁有**(權杖、手機)、**本人**(生物特徵)。
- OTP 與一般硬體權杖仍可能被釣魚;**FIDO2 / WebAuthn** 抗釣魚。
- 風險式或自適應驗證:依情境調整強度。

#### CASB

- 位於客戶與雲端服務之間,提供**可視性**、**合規**、**資料安全**、**威脅防護**。
- 部署方式:API 式(連到 SaaS 的 API)、代理式(forward proxy、reverse proxy)。

#### 機密、金鑰與憑證管理

- **保險庫(vault)**、**自動輪替**、**短期憑證**、**最小權限**、使用紀錄稽核。
- 工作負載使用**平台提供的身分**取得憑證,不用長期金鑰。

### 名詞解釋

- **Assertion**:IdP 對 SP 的身分聲明。
- **JWT**:JSON Web Token。
- **JIT access**:限時授予權限。
- **Phishing-resistant MFA**:抗釣魚的 MFA。

### 延伸知識:登入流程與授權模型

#### SAML(SP-initiated)流程

1. 使用者存取服務提供者(SP)。
2. SP 把使用者**重新導向**到 IdP,並帶上驗證請求。
3. 使用者在 IdP 完成驗證(含 MFA)。
4. IdP 回傳**簽署過的 SAML 斷言(assertion)**給 SP。
5. SP 驗證簽章,建立工作階段。

#### OIDC(授權碼流程)

1. 應用導向 IdP 授權端點。
2. 使用者驗證並同意。
3. 應用收到授權碼,向 IdP 換取 **ID token**(JWT,證明身分)與存取權杖。
4. 應用驗證 ID token 的簽章、發行者、受眾、有效期限。

#### 授權模型

| 模型 | 說明 |
|---|---|
| RBAC | 依角色授權,易管理,容易角色爆炸 |
| ABAC | 依屬性(使用者、資源、環境)動態授權,細緻 |
| PBAC / 政策式 | 以集中政策表達規則 |
| 最小權限、JIT | 只給必要權限、必要時間 |

#### 零信任(zero trust)

- 原則:**永不預設信任,持續驗證**;依身分、裝置狀態、情境逐次決策;最小權限;假設已被入侵。
- 與 IAM 的關係:身分是主要控制點。

#### 特權存取管理(PAM)

- 密碼保險庫、工作階段記錄、限時提權、審批。

### 情境演練

公司導入 SSO 後,一個員工帳號被釣魚,攻擊者登入所有應用。**根因**:SSO 集中風險但未搭配抗釣魚 MFA 與條件式存取。**改善**:改用 FIDO2、依裝置與位置做條件式存取、異常登入告警。

### 考點與陷阱

> Tip:第三方應用要讀行事曆又不能知道密碼,用 OAuth 2.0;同時要登入,用 OIDC。

> 陷阱:SSO 方便但不代表安全;若沒有 MFA,單一帳號被盜就影響所有應用。
